# Migrating lonewanderer27.github.io from Jekyll to Astro

> Status: draft plan, not yet started. Written 2026-09-11 against branch `version4` at commit `d2bf236`.
>
> Decisions taken (2026-09-11): `src/data/` is split by domain (section 3); `/resume` is a separate site already deployed at `jay.thedev.id/resume` and must **not** be generated by this project (section 7); Conventional Commits are followed by hand during the migration, with husky enforcement added as the final commit (sections 12 and 13, step J).
>
> Scope boundary: this is a build-system migration only — no CSS rewrite and no restyling of any kind happens *in this plan* (sections 8 and 14).
>
> **Amended 2026-09-11:** the original boundary also froze Bootstrap and the SCSS in place. That is withdrawn. [bootstrap-to-tailwind.md](bootstrap-to-tailwind.md) converts **all** styling — vendored Bootstrap 4 *and* the hand-written SCSS — to pure Tailwind v4 **in the Jekyll repo first**, so this migration ports templates that already carry Tailwind classes and a repo with no `.scss` files left in it. The boundary itself is unchanged in spirit: the styling rewrite and the framework port stay in separate passes, they just happen in the other order. Affected here: the scaffolding in section 2, the stylesheet handling in section 8, the deployment workflow in section 10 (whose Pages/Actions setup the Tailwind work now lands first), and the verification baseline in sections 11 and 14.

## 1. What the current setup actually does

Before planning the port, a few things about the existing site materially change the approach:

**Deployment is not what CLAUDE.md says it is.** There is no `.github/workflows` directory, and `docs/` is listed in [.gitignore](../../.gitignore) and has zero tracked files. So GitHub Pages is not serving a committed `docs/` folder — it is running its own classic Jekyll build from the root of the `version4` branch, and the `destination: docs/` setting in [_config.yml:12](../../_config.yml#L12) only affects local builds. This matters a great deal: the classic Pages build only understands Jekyll. The moment the site becomes an Astro project, you need a GitHub Actions workflow and you need to switch the Pages source to "GitHub Actions" in repository settings. That is a hard dependency, not an optional improvement, and it has to land together with the migration.

**There is a domain mismatch already.** [CNAME](../../CNAME) contains `jay.thedev.id`, while [_config.yml:4](../../_config.yml#L4) declares `url: https://lonewanderer27.github.io`. One canonical value must be picked for Astro's `site` option, since it feeds the sitemap, the RSS feed, and absolute URLs in meta tags.

**URL shapes need to be preserved deliberately.** Posts currently resolve to `/2022/04/22/the-coffee-lounge/` because of `permalink: pretty`; confirm this in the local build output under `docs/2022/`. Astro's default would give `/the-coffee-lounge`, so post routing needs a custom dynamic route. Standalone pages are emitted as `/about.html` and friends, but the navigation in [_data/settings.yml:14-20](../../_data/settings.yml#L14-L20) links to `/about`, which works because GitHub Pages serves `about.html` for an extensionless request. Astro's default directory output produces `/about/index.html`, which also serves at `/about`, so the nav keeps working — but add redirects for the old `.html` URLs in case anything out there links to them.

**Four Jekyll plugins are in use** ([_config.yml:17-21](../../_config.yml#L17-L21)) and each needs a replacement: `jekyll-sitemap` becomes `@astrojs/sitemap`, `jekyll-feed` becomes an `@astrojs/rss` endpoint at `/feed.xml` to match the existing path, `jekyll-seo-tag` (the `{% seo %}` call in [_includes/head.html:44](../../_includes/head.html#L44)) becomes a hand-written `BaseHead` component, and `jekyll-redirect-from` (used for `/projects` → portfolio in [_pages/portfolio.html:4](../../_pages/portfolio.html#L4)) becomes an entry in Astro's `redirects` config.

**The front-end stack is entirely vendored and quite old**: Bootstrap 4 CSS and JS, jQuery, slick carousel, Shuffle.js, Themify icons, and the EmailJS SDK, all sitting as minified files in `assets/plugins/`. Copy these across verbatim in the first pass and modernize nothing. Mixing a framework migration with a dependency upgrade makes any visual regression impossible to attribute.

**Assets are large but simple**: 111 files totalling 16MB in `assets/images/`. Copying them into `public/assets/images/` keeps every image URL byte-identical, which removes a whole category of risk. Astro's image optimization is worth doing later, on its own.

Finally, [_data/settings.yml](../../_data/settings.yml) is the site's real content surface, as CLAUDE.md notes — it drives the hero, about blurb, work process, experience, certificates, education, services, both portfolio lists, testimonials, client logos, contact copy, nav, and footer. This becomes typed TypeScript rather than staying YAML; sections 3 and 4 cover that in detail.

## 2. Scaffolding

Initialize Astro in place and add the dependencies the port needs:

```bash
npm create astro@latest -- --template minimal --no-git --skip-houston .
npm i -D @astrojs/sitemap @astrojs/rss @astrojs/check typescript
npx astro add tailwind          # installs @tailwindcss/vite, writes src/styles/global.css
```

No YAML loader is needed, since the data becomes TypeScript. `@astrojs/check` gives `astro check` for typechecking `.astro` files against the new types — wire it into an `npm run typecheck` script and into the `build-cmd` in section 10.

`sass` is **not** in that list, unlike the original draft: with the Tailwind migration landed first there is no Sass left to compile (section 8). Add it back only if taking that section's fallback path. `astro add tailwind` handles the Vite plugin registration itself — nothing about Tailwind belongs in the `integrations` array below.

Configure Astro:

```js
// astro.config.mjs
import { defineConfig } from 'astro/config';
import sitemap from '@astrojs/sitemap';

export default defineConfig({
  site: 'https://jay.thedev.id',
  outDir: './dist',
  integrations: [sitemap()],
  redirects: {
    '/projects': '/portfolio',      // replaces jekyll-redirect-from
    '/about.html': '/about',        // old Jekyll page URLs
    '/blog.html': '/blog',
    '/portfolio.html': '/portfolio',
    '/contact.html': '/contact',
  },
});
```

In a static build, Astro emits small meta-refresh pages for `redirects`, which is behaviourally equivalent to what `jekyll-redirect-from` was producing.

Add path aliases in `tsconfig.json` so imports stay short, extending Astro's strict base config:

```json
{
  "extends": "astro/tsconfigs/strict",
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"],
      "@data/*": ["src/data/*"],
      "@types/*": ["src/types/*"]
    }
  }
}
```

## 3. Converting the YAML data to TypeScript

Both `_data/settings.yml` and `_data/plugins.yml` go away, replaced by typed modules. The layout separates the shape of the data from the data itself:

```
src/types/
  site.ts          SiteConfig, MenuItem, SocialLink
  resume.ts        ExperienceItem, CertificateItem, EducationItem, SkillItem
  portfolio.ts     PortfolioCategory, PortfolioLabel, PortfolioItem
  content.ts       ServiceItem, WorkProcessStep, TestimonialItem, ClientLogo, TeamMember
  vendor.ts        VendorAssets
  index.ts         barrel re-export
src/data/
  site.data.ts         title, logo, banner, author, description, email, phone, copyright, menu, social, analytics, disqus
  hero.data.ts         hero title, about blurb + CTA
  resume.data.ts       experience, certificates, education, skills
  portfolio.data.ts    labels, home items, full items, CTA
  content.data.ts      services, work process, testimonials, client logos, team
  contact.data.ts      contact title and target email
  vendor.data.ts       the CSS/JS plugin paths from plugins.yml
  index.ts             barrel re-export
```

This split is the chosen layout. It roughly follows how the sections are already grouped in the current YAML, so finding things stays familiar, and the barrel in `src/data/index.ts` still gives a single import site (`import { experience, services } from '@data'`) without a 300-line one-file module.

**Keys become camelCase.** The kebab-case keys in the YAML (`blurb-btn-link`, `portfolio-home-items`, `testimonial-items`, `client-slider-items`, `portfolio-type`, `work-process`, `experience-title`) would need bracket access in JavaScript, and they are not idiomatic in TypeScript anyway.

**Use `satisfies`, not type annotations.** Writing `export const experience = [...] satisfies ExperienceItem[]` validates the data against the type while preserving literal types, so a component can still narrow on specific values. A plain `: ExperienceItem[]` annotation widens everything to `string` and throws that away.

**Name HTML-bearing fields explicitly.** Two values currently pass through Liquid's `markdownify` — `copyright` in [_includes/footer.html:29](../../_includes/footer.html#L29) and `work-process[].content` in [_includes/work-process-section.html:13](../../_includes/work-process-section.html#L13). Astro has no such filter, and pulling in a markdown library for two strings is not worth it. Convert them to inline HTML and name the fields `copyrightHtml` and `contentHtml` so that the `set:html` at the call site is obviously intentional rather than a possible XSS smell. The same applies to `hero.titleHtml`, which contains `<br>` tags, and to `blurbHtml`.

**Commented-out blocks become typed empty arrays.** The `skills` and `team` blocks in the YAML are commented out ([_data/settings.yml:81-88](../../_data/settings.yml#L81-L88) and [_data/settings.yml:76-79](../../_data/settings.yml#L76-L79)), and their components guard on existence with `{% if %}`. Export them as `[] satisfies SkillItem[]` and `[] satisfies TeamMember[]`, and have the components guard with `array.length > 0`. That preserves the current rendering exactly while keeping the shape documented for whenever they get filled in.

**Convert mechanically, then verify.** Rather than retyping 300 lines of YAML by hand, dump it to JSON first with a throwaway script in the scratchpad (`yaml` package, `JSON.stringify(parse(file), null, 2)`), then reshape the JSON into the typed modules. Once both exist, a short temporary script that deep-compares the parsed YAML against the new TS exports — after normalizing kebab-case to camelCase — will catch any dropped entry or typo'd value. It costs ten minutes and removes transcription risk from a 300-line manual edit. Delete it once green.

One tradeoff to be aware of: content edits now go through TypeScript rather than YAML, so a typo becomes a build error instead of a silently missing value. That is a net win, but it means content changes want a `npm run typecheck` or a dev-server check rather than being purely textual. CLAUDE.md needs rewriting to say so.

Derived directly from the current YAML, with optionality matching what is actually optional in the data today.

```ts
// src/types/resume.ts
export interface ExperienceItem {
  name: string;
  /** Filename within /assets/images/experience/. */
  icon: string;
  date: string;
  organization: string;
}

  name: string;
  date: string;

  name: string;

```

The `value: \`${number}%\`` template literal type is a small but real improvement: the current YAML would happily accept `70` or `"70"`, either of which would break the CSS that consumes it.

```ts
// src/types/portfolio.ts
export type PortfolioCategory = 'api' | 'desktop' | 'webapp' | 'bot';

export interface PortfolioLabel {
  title: string;
  type: PortfolioCategory;
}

export interface PortfolioItem {
  image: string;
  url?: string;
  github?: string;
  /** Overrides the default "view project" button label. */
  urlText?: string;
  /** Shuffle.js filter groups; omit for the homepage subset. */
  categories?: PortfolioCategory[];
}
```

Two notes. The `PortfolioCategory` union is the clearest single win from typing this data: right now the filter buttons in `portfolio-label` and the `portfolio-type` values on each item are independent strings, so a typo in either silently produces a filter that matches nothing. The union makes that a compile error. Second, the YAML nests categories as a list of single-key objects (`portfolio-type: [{ type: "webapp" }]`), which is a Liquid-era workaround; flatten it to `categories: ['webapp']`. That simplifies the `data-groups` construction in [_pages/portfolio.html:24](../../_pages/portfolio.html#L24) from a nested `forloop` with manual comma handling to `JSON.stringify(item.categories)`.

```ts
// src/types/content.ts
export interface ServiceItem {
  name: string;
  /** Themify icon class, e.g. "ti-wordpress". */
  icon: string;
  description: string;
  /** Highlights the card with active-bg-primary. */
  active: boolean;
}

export interface WorkProcessStep {
  title: string;
  icon: string;
  /** Rendered with set:html — was markdownify in Liquid. */
  contentHtml: string;
}

export interface TeamMember {
  title: string;
  image: string;
  designation: string;
}

export interface ClientLogo {
  logo: string;
  url: string;

/** Either an attributed testimonial or an anonymous one — never both. */
export type TestimonialItem =
  | { anonymous: true; image: string; content: string }
  | { anonymous?: false; image: string; content: string; name: string; designation?: string };
```

That discriminated union on `TestimonialItem` encodes a rule the template already implies: [_includes/testimonial-section.html:16-24](../../_includes/testimonial-section.html#L16-L24) shows "Anonymous Client" and ignores `name`/`designation` when `anonymous` is set. Currently all three testimonials are anonymous, and nothing stops someone adding a `name` that silently never renders. The union makes the two cases explicit, and the component's `{item.anonymous ? … : …}` branch narrows correctly so `item.name` is only reachable where it exists.

```ts
// src/types/vendor.ts
export interface VendorAssets {
  /** Stylesheet paths, emitted in order into <head>. */
  css: string[];
  /** Script paths, emitted in order before the page scripts. */
  js: string[];
}
```

This replaces `_data/plugins.yml`. Keeping it as data rather than hardcoding the tags preserves the "order matters" intent — jQuery must precede Bootstrap, slick, and the rest — and gives one place to look when auditing what third-party code the site loads.

1. [_includes/head.html:20-22](../../_includes/head.html#L20-L22) reads `{% if site.author %}<meta name="author" content="{{ . }}">`. `site.author` is undefined — the author lives in `settings.yml`, not `_config.yml` — and `{{ . }}` would emit nothing regardless. ## 6. Posts as a content collection

Create `src/content.config.ts` using Astro 5's glob loader:

```ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

export const collections = {
  posts: defineCollection({
    loader: glob({ pattern: '**/*.md', base: './src/content/posts' }),
    schema: z.object({
      title: z.string(),
      image: z.string(),
      excerpt: z.string(),
      tags: z.array(z.string()).default([]),
      author: z.string(),
      imageSource: z.string().optional(),
      imageSourceUrl: z.string().optional(),
    }),
  }),
};
```

Zod schemas are the type source for collection entries — do not hand-write a `Post` interface in `src/types/`. Use `CollectionEntry<'posts'>` from `astro:content` wherever a component takes a post, so the schema stays the single definition. Rename the `image_source` and `image_source_url` front matter keys in the two affected posts to camelCase to match the rest of the codebase.

Move all three files from `_posts/` into `src/content/posts/`, keeping the `YYYY-MM-DD-slug.md` filenames, and strip the now-meaningless `layout:` key from their front matter.

Two details need care. First, **dates**: Jekyll derives a post's date from its filename, and Astro does not. Either add an explicit `date:` field to each post or parse it from the entry id in `getStaticPaths`. Parsing keeps the filename as the single source of truth — preferred. Second, **excerpts**: [_includes/post.html:9](../../_includes/post.html#L9) runs `excerpt | markdownify | strip_html | truncatewords: 30`. Two of the three posts declare `excerpt` in front matter, but `2022-08-15-pitfalls-in-working-as-a-first-time-freelancer.md` does not, so Jekyll auto-derives it from the first paragraph. The schema above makes `excerpt` required, which means backfilling that one post — considerably simpler than reimplementing Jekyll's auto-excerpt behaviour.

To preserve the post URLs, use a catch-all route at `src/pages/[...slug].astro`:

```ts
export async function getStaticPaths() {
  const posts = await getCollection('posts');
  return posts.map((post) => {
    const [y, m, d, ...rest] = post.id.split('-');
    return { params: { slug: `${y}/${m}/${d}/${rest.join('-')}` }, props: { post } };
  });
}
```

Verify the generated paths against the three directories that exist under `docs/2022/`.

### `/resume` belongs to a different site

The nav entry at [_data/settings.yml:18](../../_data/settings.yml#L18) points at `/resume`, which is a **separate project of yours already deployed at `jay.thedev.id/resume`** — it is not part of this repository and must not become part of it. Three consequences, and the first two are easy to get wrong:

1. **Do not create `src/pages/resume.astro`.** If this project ever emits a `/resume/index.html`, it will shadow the real resume site at that path, because both answer on the same host. Keeping the route absent is the requirement, not an omission. Worth a comment next to the menu entry in `site.data.ts` saying exactly that, since a future reader will otherwise "fix" the apparently-dangling link.
2. **The sitemap must not claim it.** `@astrojs/sitemap` only enumerates routes Astro actually builds, so as long as point 1 holds this is handled automatically and no `filter` option is needed. But if a `resume` page is ever added for any reason, it would silently appear in `sitemap-index.xml` and start competing with the real site in search results. Include `/resume` in the step-I deploy checks for that reason.
3. **Routing has to survive the deploy change.** This is the part that needs verifying before step I. GitHub Pages serves exactly one build per custom domain, so `jay.thedev.id/resume` cannot be coming from this repository's Pages deployment — something upstream (a Cloudflare rule, a proxy, or a redirect) must be routing that path elsewhere. Find out what, and confirm it sits in front of the Pages origin rather than depending on the current Jekyll build, before flipping the Pages source. Switching from a branch build to an Actions build does not change the origin's hostname or certificate, so the expectation is that nothing breaks — but that expectation should be checked rather than assumed, because a broken resume link is a silent failure nobody reports.

The nav link itself needs no code change: `Header.astro` renders it as an ordinary `<a href="/resume">`, and the active-state comparison against `Astro.url.pathname` simply never matches, which is correct. If you want the cross-site nature visible in the data rather than only in a comment, `MenuItem` could gain an `external?: boolean` — optional, and the only reason to bother is that the GitHub menu entry is genuinely off-domain and currently gets no `rel="noopener"`.

## 8. Stylesheet

> **Amended 2026-09-11.** This section originally read "relocated, not touched" and froze Bootstrap and the SCSS in place. That boundary is withdrawn: [bootstrap-to-tailwind.md](bootstrap-to-tailwind.md) converts **all** styling to pure Tailwind v4 and is sequenced to land **before** this migration, so the templates this port converts already carry Tailwind classes. Which of the two paths below applies depends only on whether that work has landed when this migration starts.

### If the Tailwind migration has landed (the planned order)

There is no Sass left to relocate at all — `assets/scss/` is gone, and so are `assets/plugins/bootstrap/` and the `sass:` config block. Instead:

1. Run `npx astro add tailwind`. On Astro ≥5.2 this installs `@tailwindcss/vite`, registers it, and writes `src/styles/global.css` containing `@import "tailwindcss";`. Tailwind 4 is **not** an `integrations: []` entry — that was the now-deprecated `@astrojs/tailwind` — so section 2's `integrations: [sitemap()]` stays as it is.
2. Move the body of `_tailwind/main.css` into `global.css` verbatim: the `@plugin "@tailwindcss/typography"` line, the `@custom-variant dark`, the `@theme` block (tokens, pinned breakpoints, and the `wave` keyframes), the `@utility container-page` block, `@layer base`, and the `@view-transition` block.
3. Retarget the `@source` directives. They currently point at Jekyll's template dirs (`../_includes`, `../_layouts`, `../_pages`, `../_posts`, `../_data`, `../index.html`, `../404.html`); they become `../**/*.astro` plus `../**/*.md` for post bodies. **Getting this wrong fails silently** — Tailwind generates only the classes it finds, so a bad `@source` yields an unstyled page rather than a build error. Keep the CSS-size assertion from that plan's section 13 in CI here too.
4. Import it once in `Base.astro` with `import "../styles/global.css";`, which is the documented pattern — put it in the layout so every page sharing that layout inherits it.
5. Drop `sass` from the section 2 dependency list; nothing compiles Sass any more. Add `@tailwindcss/typography`, which the post layout now depends on for markdown bodies.
6. Convert the four Liquid UI partials from that plan's section 9 (`ui/button.html` and friends) into `.astro` components. Their variant strings were compared in Liquid `case` blocks; as Astro components they become typed props, which is a straight upgrade and fits the type layer in section 4. Keep the utility strings literal in one place — do not build class names by concatenation, for the same silent-failure reason as step 3.

The `/assets/scss/style.css` URL disappears either way, replaced by a hashed bundle. Nothing external references it.

### If the Tailwind migration has *not* landed

Fall back to the original plan: move `assets/scss/` — all five partials plus the `templates/` subdirectory — to `src/styles/`, contents unchanged. Delete the empty `---` / `---` front matter block at the top of `assets/scss/style.scss`; that is a Jekyll marker and Sass will reject it. Import it once in `Base.astro` with `import '../styles/style.scss'` and let Astro handle bundling and minification, making the old `sass: style: compressed` setting unnecessary. Bootstrap and the other vendored stylesheets are then copied verbatim into `public/assets/plugins/` and referenced from `vendor.data.ts` exactly as today (sections 3 and 9).

Do **not** attempt the Tailwind rewrite inside this migration. That is the same reasoning this plan applies to the vendor JavaScript in section 9: a visual regression with two candidate causes — the framework port or the CSS rewrite — costs far more to diagnose than the two passes cost to do separately.

## 9. The vendor JavaScript — the one genuinely risky part

`assets/js/script.js` is a single jQuery IIFE loaded on every page, and it assumes homepage DOM throughout:

- The sticky-nav scroll handler on `.navigation` is fine everywhere.
- The `window.onload` block reads `#l2` through `#l9`, the hero parallax layers, which only exist on the homepage. It throws on `/about`, `/blog`, and `/contact`.
- `new Shuffle(document.querySelector(".shuffle-wrapper"))` runs unconditionally and throws on any page without a shuffle wrapper.
- The two `.slick()` initializations are harmless no-ops off the homepage, but noisy.

There is also a real conflict: `assets/js/emailForm.js` assigns `window.onload` as well, so the two files overwrite each other and only the last one loaded takes effect. The parallax block in [assets/js/script.js:73-106](../../assets/js/script.js#L73-L106) contains a commented-out copy of the same form handler, which suggests this was already being fought with at some point.

The plan: split the file into `public/assets/js/nav.js`, `parallax.js`, `shuffle-filter.js`, `sliders.js`, plus the existing `emailForm.js`; guard each one with an element-existence check; convert both files from `window.onload` assignment to `DOMContentLoaded` listeners so they stop clobbering each other; and include them per-page through a typed `scripts?: string[]` prop on `Base.astro`. jQuery, Bootstrap, slick, Shuffle, and the EmailJS SDK stay as plain `<script>` tags served from `public/assets/plugins/`, driven by `vendor.data.ts` so load order stays explicit.

## 10. Deployment

Follow [Astro's GitHub Pages guide](https://docs.astro.build/en/guides/deploy/github/) rather than hand-rolling the steps. Its `withastro/action` is a composite action that detects the package manager from the lockfile, installs, restores an Astro build cache, builds, and **uploads the Pages artifact itself** — so `actions/configure-pages` and `actions/upload-pages-artifact` are not needed at all.

Add `.github/workflows/deploy.yml`:

```yaml
name: Deploy to GitHub Pages
on:
  push:
    branches: [version4]        # or whichever branch this lands on
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: withastro/action@v6
        with:
          node-version: 22
          build-cmd: npm run typecheck && npm run build

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v5
```

The `build-cmd` input is what keeps the typecheck gate from section 12 — worth having now that the site content is TypeScript, since it turns a bad content edit into a failed CI run rather than a deployed page with a blank section. Without it the action runs a plain `astro build` and the typecheck never happens.

Two defaults worth overriding or at least knowing: `node-version` defaults to `24` and `out-dir` to `dist`. The `outDir: './dist'` in section 2 matches the default, so leave `out-dir` alone; pin `node-version` so CI does not move under the build. Versions above verified against each repo's latest release on 2026-09-11 — `checkout` v7.0.1, `withastro/action` v6.1.2, `deploy-pages` v5.0.1.

**Commit `package-lock.json`.** Astro's guide calls this out explicitly, and `withastro/action` detects the package manager *by scanning for a lockfile* — without one committed, package-manager detection is the thing that breaks. This also reverses the current repo habit, where [.gitignore](../../.gitignore) deliberately ignores `Gemfile.lock`.

Put `CNAME` in `public/CNAME` — Astro copies `public/` through verbatim, and without it the custom domain breaks on the first deploy. Because `jay.thedev.id` is a custom domain, `site` is `'https://jay.thedev.id'` and **no `base` is set**; `base` is only for project sites served from `username.github.io/repo-name`. Section 2 already has this right.

Then, in repository settings, change Pages → Source to **GitHub Actions**. That step is manual and cannot be scripted. Note that deploying via artifact means GitHub's own Jekyll processing is out of the picture entirely, so no `.nojekyll` file is needed.

Cleanup on the same branch: delete `Gemfile`, `.ruby-version`, `_config.yml`, `_data/`, `.jekyll-cache/`, and `docs/`. Rewrite `.gitignore` — drop the Ruby and Jekyll entries (`*.gem`, `.bundle`, `_site/`, `docs/`, `.sass-cache/`, `.jekyll-cache/`, `.jekyll-metadata`) and add `node_modules/`, `dist/`, and `.astro/`. Finally, rewrite `CLAUDE.md`: every command and nearly every path in it becomes wrong, and the "primary file to edit for content changes" guidance needs to point at `src/data/*.data.ts` with a note that the types live in `src/types/`.

## 11. Verification

The most valuable check is a mechanical before-and-after comparison, so capture the baseline before deleting anything Ruby-related:

1. Run `bundle exec jekyll build` on `version4` and copy the resulting `docs/` into the scratchpad as a snapshot.
2. Deep-compare the parsed YAML against the new TypeScript exports (the throwaway script from section 3) to prove no content was lost in the conversion.
3. Run `npm run typecheck` and `npm run build` to produce `dist/`.
4. Diff the two file trees. Every path in the snapshot must either exist in `dist` or be covered by a `redirects` entry. This catches URL regressions without any judgement calls.
5. For each page, diff the stripped text content and the list of `href` and `src` attributes, old versus new. Step 2 proves the data survived; this proves it reached the right places in the markup.
6. Then a manual browser pass on the things static diffing cannot see: hero parallax, testimonial slider, client logo slider, portfolio shuffle filtering, contact form submission, nav active state, the mobile menu toggle, and view transitions moving between `/`, `/about`, and `/portfolio`.

9. Note that `docs/robots.txt` and `docs/redirects.json` currently contain `http://localhost:4000` — those are artifacts of a local dev build and are untracked, so ignore them, but do confirm the production sitemap uses the real domain.

## 12. Commit conventions

The existing history already follows [Conventional Commits](https://www.conventionalcommits.org/) (`feat: add banner image support…`, `docs(posts): remove some posts`), so the migration continues that rather than introducing a new style. The rules below are what the commit sequence in section 13 is built on.

> **Amended 2026-09-11.** [bootstrap-to-tailwind.md](bootstrap-to-tailwind.md) section 12 adopts these same rules for the styling project that now lands first, so the two read consistently in `git log`. Two intended differences: its scope vocabulary mirrors the Jekyll layout (`includes` rather than `components`, no `types`/`data`), and it uses `perf` for its two payload-reduction commits where this plan reserves that type. Enforcement still belongs here — that project follows the convention by hand and leaves commitlint and husky to step J below, so the hook never sits between you and a long mechanical port.

**Format.** `<type>(<scope>)!: <subject>`, subject in the imperative mood and lowercase, no trailing period, ideally under 50 characters. A body is included only when the "why" is not obvious from the subject, wrapped at 72 columns. Footers carry `BREAKING CHANGE:` and the `Co-Authored-By:` attribution line.

**Types, and how they apply here.** The distinction that matters most on this migration is `refactor` versus `feat`. Almost every commit is a *port*: the rendered output is meant to be identical, so `refactor` is the honest type even though large amounts of new code appear. Reserve `feat` for genuinely new capability that had no Jekyll equivalent, and `fix` for the three pre-existing bugs from section 5 and the script conflict from section 9.

| Type | Used for |
|---|---|
| `build` | Astro toolchain, `package.json`, `tsconfig.json`, `astro.config.mjs`, dependency changes |
| `refactor` | Porting existing layouts, components, pages, data, styles, and scripts with no output change |
| `feat` | The new type layer, the RSS endpoint, anything without a Jekyll counterpart |
| `fix` | The `og:image` path, the author meta tag, the header `elsif`, the `window.onload` clash |
| `ci` | The GitHub Pages deploy workflow |
| `chore` | Jekyll teardown, `.gitignore`, housekeeping |
| `docs` | `CLAUDE.md`, `README.md`, this plan |
| `perf` | Nothing in this migration — reserved for the phase-2 work in section 14 |

**Scope vocabulary.** Fixed set, mirroring the directory layout so scopes stay predictable: `config`, `deps`, `types`, `data`, `layouts`, `components`, `pages`, `content`, `styles`, `scripts`, `assets`, `seo`, `ci`. Omit the scope only where a change genuinely spans everything, which on this plan is just the teardown commit.

**Breaking changes.** Exactly one commit is breaking: removing the Jekyll build system, because it requires a manual repository-settings change that no amount of committed code can perform. It gets both the `!` marker and an explicit footer:

```
chore!: remove jekyll build system

The classic GitHub Pages Jekyll build no longer applies now that the
site is built by Astro in CI. Removes Gemfile, .ruby-version,
_config.yml, _data/ and the local docs/ output directory.

BREAKING CHANGE: GitHub Pages must be switched from branch-based
building to "GitHub Actions" in repository settings, or the site will
serve stale content after this commit. Page URLs move from /about.html
to /about/; the old paths are preserved by meta-refresh redirects.

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

**Atomicity and green commits.** Each commit does one thing and is individually revertable, but mid-port the site cannot build cleanly at every single commit — a ported layout referencing components that do not exist yet is unavoidable. The green points are the *step* boundaries in section 13, not every commit. Do not paper over this by squashing everything into one commit; keep the granularity and merge the branch with a merge commit or a rebase rather than a squash, so the history survives. The pull request title follows the same convention: `refactor!: migrate site from jekyll to astro`.

**Keep fixes out of refactors.** When porting a component surfaces one of the known bugs, land the faithful port first and the correction as its own `fix:` commit immediately after. Mixing them makes the diff that changed rendered output indistinguishable from the diff that merely changed syntax, which defeats the verification approach in section 11.

**Enforcement comes last, as its own commit.** The convention is followed by hand throughout the migration; husky and commitlint are added in step J, after the site is live on Astro. That ordering is deliberate: a `commit-msg` hook installed at the start would be enforcing a scope vocabulary that is still being invented, and any hook misconfiguration would block the migration commits themselves rather than being an isolated problem.

The final commit adds `@commitlint/cli` and `@commitlint/config-conventional` as dev dependencies, a `commitlint.config.js`, a `.husky/commit-msg` hook running `npx --no -- commitlint --edit "$1"`, and a `"prepare": "husky"` script. Two configuration notes:

- Set `scope-enum` from the fixed vocabulary above, so an invented scope fails instead of quietly entering the history. This makes section 12 of this document and `commitlint.config.js` two copies of the same list — when one changes, change both.
- `config-conventional` defaults to a 100-character header and 100-character body lines. Set `header-max-length` to 72 and `body-max-line-length` to 72 to match the format rules above. The 50-character subject target stays a convention rather than a hard limit, since a single rule cannot both warn at 50 and fail at 72.

Use `"prepare": "husky || true"` so that `npm ci` in the deploy workflow does not fail in an environment where hook installation is not wanted. Optionally add a commitlint job that validates pull request titles too, since a squash merge would otherwise take the PR title unchecked — though this plan merges rather than squashes.

Doing types (B) before data (C) and data before components (D onward) means every later step gets autocomplete and compile-time checking for free, and any shape mistake surfaces at the point where it is cheapest to fix. Run A through H on a branch off `version4`. Keep I separate and last of the migration proper, since flipping the Pages source is the one step with real blast radius, and note that its `chore!` commit is the point of no return for the old pipeline. Rollback before that commit is a branch delete; after it, revert the merge and switch the Pages source back to a branch build.

Step J lands after the site is confirmed working, so the hook never sits between you and a migration commit. Its two commits can go on their own small branch and pull request — the enforcement change has nothing to do with Astro, and keeping it separate means `git log` shows a clean boundary between "the site moved to Astro" and "the repo started enforcing commit format". Verify it by attempting a commit with a message like `updated stuff` and confirming the hook rejects it.

## 14. Deliberately out of scope

Worth doing eventually, but not during the migration, because each one would obscure whether a regression came from Astro or from the change itself:

Adopting Astro's `<Image>` component for the 16MB image directory; replacing slick with a vanilla carousel; replacing Shuffle.js with CSS grid plus view transitions; moving to GA4 (the include at `_includes/google-analytics.html` uses the long-retired `analytics.js`, though it is currently disabled since `google-analytics` is empty in settings); and swapping Disqus for Giscus.

**Styling and CSS frameworks are out of scope entirely**, not merely deferred to a later phase of this plan. No class names change anywhere *during this migration*. This keeps the output-diffing verification in section 11 meaningful: as long as class names are preserved, the rendered HTML can be compared mechanically against the Jekyll baseline. Any styling change breaks that check and turns verification into visual comparison, which is the reason to keep the two kinds of work apart.

> **Amended 2026-09-11.** The reasoning above stands unchanged, but the baseline it compares against has moved. Since [bootstrap-to-tailwind.md](bootstrap-to-tailwind.md) now lands first, the section 11 baseline must be captured from a **post-Tailwind Jekyll build**, not from `version4`. Capturing it from `version4` would fold the entire CSS rewrite into this migration's diff and destroy exactly the mechanical comparison this section is protecting. Concretely: section 11's step 1 says to run `bundle exec jekyll build` on `version4` — that must instead run on the branch where the Tailwind work merged.
